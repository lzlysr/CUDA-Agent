## 1. 结论与证据范围

**可以进入 P2 的开发和小规模验通；还不具备直接启动 150 步正式单轮 PPO 的条件。**

P0 已提供环境及短序列模型组件的历史验通依据；当前环境和依赖身份仍可核实。P1 已实现原论文开发环境的主要能力：官方 SKILL、多文件 CUDA 实现、文件和持久终端工具、CPU/GPU 解耦、五例反馈、eager/compile 对比、离散奖励及轨迹最佳候选选择。它是一套可运行的本地推理与评测基线，尚不是训练系统。

剩余工作不应再以不断修改模型生成的数学错误为主，而应转向：冻结评测与奖励合同、补齐训练数据与 token 记录、恢复可维护的 actor/critic 适配、接入 verl、验证在线权重同步和训练恢复，然后小规模 PPO。

| 判定 | 含义 |

## 7. 正确性、性能与奖励：哪些对齐，哪些改变口径

### 7.1 正确性

| 项目 | 官方/论文 | 本地 | 评估 |
|---|---|---|---|
| 参数一致 | 候选加载原始 state_dict | 多组固定参数，strict=True | 核心对齐，约束更明确 |
| 五个反馈输入 | p.6；官方 verification.py:85–95 | 5个输入，固定种子重复使用 | 数量对齐；跨次重采样方式不同 |
| 数值容差 | atol=rtol=.01 | 同一容差，外部 CPU 比较全部元素 | 核心对齐，未通过分块减少比较量 |
| 输出结构 | 类型/序列/张量比较；官方字典只查预期键 | 类型、shape、dtype、完整键集合、有限值 | 更严格本地合同 |
| 参考/候选执行 | 官方示例同进程 | 两容器、外部评分器、独立输出通道 | 合理隔离改进，会增加初始化与传输成本 |
| 隐藏验收 | 原文/公开脚本无相同协议 | 2初始化×5输入×3检查+4=34次比较 | 本地扩展，不能称论文要求34次 |
| 重复/改输入/乱序/重载 | 未公开同样集合 | 隐藏中检查 | 防缓存/状态问题的工程扩展，仍非穷尽证明 |

隐藏的34次不等于34个完全独立新样本：包含重复调用；输入扰动主要是浮点张量第0维翻转或标量取负，整数/布尔不变；某些浮点输入变换后也可能不变。隐藏种子固定，“隐藏”主要是结果不反馈模型，不代表执行程序无法推知种子。

### 7.2 性能

官方公开 profiling：同一进程先测候选，再 eager，再 compile；warmup5、默认10次；torch.profiler 的 CUDA 事件总时间除以次数。当前：独立容器按参考前测→候选→参考后测；5组输入轮换，各预热一次；3轮×30次，轮内/轮间中位数；CUDA Event 为主，wall-clock 另记，profiler 独立运行。

两者**不是同一个计量协议**。CUDA Event 流间隔包含的 launch gap/串行等待，与 profiler 活动事件求和不同；平均数和中位数也不同。当前实现可保留为既定公平测时协议，但不得把本地数字直接等同论文主表。

本地 compile 同官方一样使用默认模式，未设 fullgraph=True；编译首调成本单列，不混入稳态延迟。compile 基线内部可能生成 Triton，这与“候选禁止 Triton”不是冲突。

当前配置漂移阈值 **10%**；V7/V9 冻结配置是5%，原计划是3%。阈值没有论文公开的对应值。当前不应偷偷改回任一旧值，也不应在不说明的情况下将跨阈值运行混为同协议。特别是奖励里程碑仅5%，容许10%前后漂移时，接近里程碑的奖励需要用重复证据评估可靠性；10%上限不等于每个测量都误差10%，也不保证误差小于5%。

代码：`worker.py:379–447,512–573`，`evaluation.py:981–1109`。

### 7.3 TF32、合同与反 reward hacking

双方新进程统一 TF32，禁止候选改全局精度，参考和候选隔离，保留本地已讨论确定的方案。无需为“对齐”恢复官方脚本的同进程状态污染。

原 PDF p.31 图18本身在 forward 内以 torch.rsqrt/算术折叠BN，并在末尾把TF32关闭；这与 SKILL 禁止Torch计算存在冲突，又能影响同进程后跑基线。当前合同会拒绝这种实现。cuDNN Conv本身则是官方明确允许的路径，不能把调用厂商库一概当作弊。

目前自动检查仍有边界：

- 允许的 `.h/.cuh` 没有和 `.cu/.cpp` 一起进入静态内容扫描（`contract.py:164–200`）。
- 运行期回退只对测时后第一组输入的一次 forward 进行 profiler；verify-only/hidden 没有同样的动态回退检查（`worker.py:532–537`，`evaluation.py:918–923`）。
- cuBLAS 只用于 GEMM、cuDNN只用于Conv的用途，Conv必须cuDNN等未被完整语义认证。
- runtime_fallbacks 允许的创建、视图、复制/转换等是本地工程白名单；原论文没有公布逐项相同表。它们不是全都“纯元数据”。此处保留已约定实现，不重新否定已有决策。
- `case_storage_limit_bytes` 目前用于共享内存空间选择，**不是已执行的8GB输出/输入快照硬上限**；读取前没有对应体积拦截（`helper/stream_transport.py:14–25`）。
- 目前强制至少一份 `.cu`，可能误拒只用合法cuBLAS/cuDNN包装的候选；固定文件/类型/头文件和路径检查仍不能视为形式化安全证明。

没有发现当前已有通过候选利用上述缺口作弊；这里记录的是训练优化奖励前需要知道的覆盖范围。P2最小准入应补齐明显可执行的源码覆盖和资源上限，不要求先证明绝对不可攻击。

### 7.4 奖励和选优

`evaluation.reward` 与 p.5 式(1)一致：错误 -1；正确1；耗时严格小于 eager 的.95给2；同时严格小于 compile 的.95给3。仅快过compile而未快过eager仍给1，恰好.95不升级。5%耗时下降对应 speedup>1/.95≈1.05263，而不是简单speedup>1.05。

最终评测按相对compile最大加速选择轨迹候选，与 p.8 的方向对齐。本地还会按该顺序尝试隐藏验收，失败再检查下一候选。隐藏没有反馈模型继续优化，但参与候选选择，不能称完全未参与选择的一次性独立测试。

**选优规则不能直接当训练奖励规则。**P2是一次输出，天然对这一份输出评分；后续多轮训练须明确终局奖励归属，不能把任意历史最佳候选的奖励错贴到后续失败动作或不对应的token序列。

## 8. 指标与当前实际结果

### 指标

- Faster Rate 是正确且 speedup>1 的任务比例；论文不把5%奖励门槛直接当 Faster Rate定义。
- GM Speed-up 只在正确解上求几何平均；本地进一步要求有效测时。无有效样本返回 null，不填0。
- 当前 `summary.json` 有 faster_eager/compile 的**数量**，没有完整显式 Faster Rate分母字段；自行算率需固定以全部题还是有效题为分母。

## 12. P2能否直接启动：实际缺少的接口

### 12.1 已有的可复用资产

- 固定基座、训练依赖和官方verl源码。
- train任务记录、任务接口、原始SKILL与prompt拼接函数。
- 严格single解析、多文件写入、候选冻结。
- 编译/正确性/性能/奖励控制器与独立评测卡池。
- 运行留证和部分基础设施错误处理经验。

### 12.2 不能把当前P1当作训练入口

当前src只有p1，scripts只有P1入口，configs只有P1 JSON；没有项目级PPO配置、训练任务适配、reward manager、actor/critic构造入口或训练checkpoint目录。

`Pilot.generate`取回了vLLM的token_ids，却只保存长度；没有请求/保留逐token旧策略logprob。`turn_log`保存文本、工具和统计，没有完整输入/输出token序列、assistant mask、policy version或bootstrap信息。重新解析、重新套模板、重新分词不保证与当时采样token完全一致。

另外，`compile_only` 的 `scored=False` 及骨架中的 -1 不是训练负奖励；`evaluate(final=True)` 只验隐藏正确性，成功返回的 reward=1 也不能覆盖反馈阶段可信性能得到的2/3。训练适配器必须明确使用哪个阶段的有效奖励，而不能从任意一个 result.json 抽取 reward 字段。

所以：

- 旧P1日志可作人工分析；经过明确构造后可作某些监督数据素材。
- **不能直接作为可追溯的on-policy PPO训练batch。**应通过新训练采样路径重新产生所需数据，而不是事后伪补old logprob。
- P1逐题完成恢复，不等于actor/critic/optimizer/scheduler/RNG/数据游标/策略版本的训练恢复。

### 12.3 框架已有能力，不等于项目已接通

当前verl有Qwen3.5专门模型实现、FSDP value head后处理、LoRA和vLLM同步逻辑；当前Transformers也有Qwen3.5 token classification模型。这为接入提供基础，**没有证据支持“这个模型完全无法接critic”**。

但当前P1没有使用这些训练接口，P0短测试也没有运行完整的Ray/FSDP/rollout同步链。因此实际构造、语言层LoRA范围、视觉/MTP冻结、GDN反向、value head保存、padding/packing和同步仍须端到端验证。

并且verl默认参数不是论文配方：当前默认lambda=1、upper clip=.2、LoRA rank=0、actor LR1e-6、critic LR1e-5等，不会因安装了verl就自动变成lambda=.95、upper clip=.28或计划LoRA配置。

代码：`third_party/verl/verl/trainer/config/ppo_trainer.yaml:71–78`；`actor/actor.yaml:36–42,148–151`；`critic/critic.yaml:16–19`；`model/hf_model.yaml:43–49`；`workers/engine/fsdp/transformer_impl.py:1594–1644`。

## 13. 推荐的下一步及明确门槛

### P2-A：训练接入前冻结与最小收口

不需要为此跑完整test或KernelBench，也不继续逐个修模型答案。

1. 冻结当前实现及运行身份，保留V7/V9与进行中的V8；同步清理文档中陈旧的GPU、并发、隐藏数量、漂移值等说法。当前P1报告同时存在3%/5%和旧GPU示例，不能作为唯一参数真值。
2. 修正题目seed派生，使同题在不同子集中的采样seed稳定；保留“后端/并发可能改变数值轨迹”的说明。
3. 为训练定义“可用奖励/候选失败/环境失败”：真实格式、编译、执行、数值或合同失败给-1；可信正确解给1/2/3；参考故障或无效计时不伪装成模型-1，按固定重试/丢弃补采策略处理。保留详细证据，防止通过无限重试挑好分。
4. 将可include头文件纳入审查，落实声称的输出/快照容量上限，明确纯厂商库合法候选的处理。这里做最低限度修补，不另建复杂工具系统。
5. 为P2单独冻结奖励使用5反馈还是额外隐藏、漂移门槛、终止/截断语义、single交付合同。沿用已批准协议是最小变更；若为训练成本改为5例奖励/隐藏抽审，需要明确记录为新训练协议，不能擅自移除隐藏验收。

### P2-B：真正的单轮PPO小闭环

实现路径应是：

`train任务 → 固定prompt/SKILL → verl rollout生成一次 → 严格解析多文件 → 可信Evaluator → terminal reward → critic values/GAE → PPO actor+critic更新 → 权重同步回rollout → 下一批`

采用PPO和critic，保留论文单轮warm-up阶段；不默认改成无critic的GRPO，也不默认增加教师蒸馏或SFT格式修补阶段。

最低验收内容：

- actor语言层LoRA与critic head确实更新；冻结的基座/视觉/MTP不误更新。
- rollout、old-policy重算与训练使用相同token身份和采样约定；mask不覆盖prompt/工具输出；记录policy version。
- gamma=1、lambda=.95、ratio clip[.8,1.28]等显式设置；LR/batch/LoRA是论文值还是本地变体逐项注明。
- 先做1–2步短序列接线验证，再做约10步小规模真实任务闭环；短序列只验接口，不能冒称32K容量通过。可信fixture可验奖励/梯度链，不能算模型成功样本或混入正式能力结果。
- LoRA更新后vLLM确实用到新权重；prefix/GDN状态与缓存不会让下一批沿用旧策略。最初可在P2独立配置中简化开关，随后逐项验证，不改正在跑的P1。
- 数值、logprob/importance ratio尾部、value loss、有效奖励率、格式失败率、生成长度和显存/时间可解释；不能仅看平均reward。
- 保存退出再恢复，继续更新；actor/critic/优化器/调度器/RNG/策略版本/采样位置都保留。

### P2-C：通过后才放大

验收目标上下文32768，32K包含prompt与response总长，不是response另加32K。A100上的LoRA/FSDP资源安排先实测；P1生成并发4不能直接当训练并发4。

原计划batch24/minibatch12、actor/critic LR3e-5/6e-5、rank64/alpha128是合理的待验证本地起点，不是本次已经证明最优或原作者超参。训练/rollout资源池与评测卡分开，先估算每步编译/验算/更新成本，再决定150步正式预算。

小闭环通过后再进入P2主实验；随后按P3→P4→P5→P6推进。论文论证需要RFT和价值预训练，不能因当前基座Agent有错误就跳过warm-up，也不能直接从原始Qwen进入完整多轮PPO后把崩溃当论文无效。

## 14. 如何看当前低通过率

V7单轮0/9、Agent2/9以及V9最终0/4，说明**当前基座在当前任务/合同下的起点较弱**，并不证明原论文训练方法无效。论文p.9的single-turn比较已经经过单轮训练；当前P1没有训练，这是实验阶段区别。

也不能把所有失败都归模型：V9 hardsigmoid是测时有效性问题；此前确实有工具/编译边界工程错误，已经逐步修复。现在对已确认的数学、索引、边界和API生成错误，应保持用户要求，只记录，不人工修答案。

如果P2小批量采样持续得不到任何有效正确解，奖励几乎全为-1，学习将缺少正向区分；但**不设置“基座必须先达到某通过率才准进入P2”的伪论文门槛**。应先验证奖励有区分能力、统计一个预先固定train小批的信号，再决定是否需要课程采样或额外训练启动措施。若加入教师SFT/格式预热，须单独说明那是新的方法变体并与用户讨论，不能当作原论文已有阶段。

## 15. 原论文自身的边界

1. 摘要/引言的L1/L2/L3 Faster Rate为100/100/92%，p.7表1则是97/100/90%；表1整体compile Faster Rate96.8%。不能把两组数当同一实验口径。
2. p.6叙述稳定训练200steps，p.8设置150steps；另有150/200turns，不能用turns解释steps差异。
3. p.31图18行为与严格SKILL合同冲突，也存在TF32污染风险；不应为了“完全对齐”复制这一行为。
4. 原文未完整公开软件栈、采样、RFT/VP训练量和私有评测器。作者后来Seed2.1、FlashInfer比赛、Opus4.7材料属于后续工作，不补写成原始论文的方法证据。

因此，本项目应定位为：**基于公开论文、Ops-6K和官方开发约定，用Qwen3.5-9B重建多阶段Agentic RL方法，并明确报告本地协议与资源差异。**

下一阶段最值得做的是P2训练接入及小闭环，而非重做公开数据合成/去污染、无止境改提示词、抢跑完整test/KernelBench，或直接启动尚无训练入口的150步主训练。
